# Netlify — procedimiento candidato de entrega manual

**Misión 005.2-NETLIFY · 2026-10-17 · NO-GO para despliegue.** Netlify es el proveedor **candidato** para la primera previsualización editorial; Cloudflare Pages Direct Upload continúa como alternativa técnica documentada en `HOSTING-COMPARISON.md` y `MISSION-005-DECISION.md` (decisión histórica, no vigente como elección del propietario). Esta guía no autoriza crear un proyecto, contratar un plan, conectar GitHub, cambiar DNS ni subir archivos. `publicationAllowed=false`; no se publican CSV, derivados, filas ni importes.

## Artefacto local y configuración

El único directorio candidato de publicación es `packages/web/out/`, generado con `output: "export"` y `trailingSlash: true`. Contiene HTML de seis rutas, páginas de error, TXT de Next, JS/CSS y el archivo raíz `_headers`. **No subir** la raíz del repositorio, `.next/`, `data/`, originales ni un ZIP sin extraer. Netlify lee reglas de `_headers` cuando el archivo está físicamente en el directorio publicado; las cabeceras se aplican a archivos estáticos servidos por Netlify, no a respuestas de Functions, proxy, Edge Functions o SSR. La regla `/*` propone una CSP común `Content-Security-Policy-Report-Only` con hashes de los inline del export exacto, más `nosniff`, `no-referrer`, Permissions Policy y denegación de frames. No se usa `'unsafe-inline'` ni nonce fijo; HSTS queda pendiente de probar HTTPS/dominio. `_headers` local **no prueba** que las cabeceras se apliquen en Netlify ni que un navegador no informe violaciones. No se añade `_redirects`: Netlify documenta Pretty URLs habilitadas por defecto y `404.html` raíz para rutas inexistentes; un rewrite SPA `/* /index.html 200` ocultaría el 404.

Orden reproducible desde un checkout limpio **sin originales ni datos privados**, sólo tras permisos para instalar/ejecutar dependencias cuando correspondan:

1. Revisar commit, `git status --porcelain=v1`, `bun.lock` y dependencias; usar Bun 1.4.3 y, en un entorno limpio autorizado, `bun install --frozen-lockfile --ignore-scripts`. En el entorno ya instalado, no reinstalar por esta guía.
2. Ejecutar `bun run lint`, `bun run test`, typechecks directos de core/ingestion/web y `bun run web:verify`. Este último reconstruye `out/`; **siempre debe terminar antes de generar `_headers`**. La integración externa omitida no equivale a prueba aprobada.
3. Generar `bun scripts/netlify-headers.ts generate`. El generador exige las nueve rutas HTML y crea `out/_headers` sin sobrescribirlo; si existía de un build previo, detenerse, revisarlo y retirarlo de forma deliberada antes de regenerar. Revisar política y hashes; cambios en HTML o contenido inline obligan a repetir desde el build. El generador decodifica `&quot;` si aparece en atributos `style`; una entidad distinta o marcado no analizable obliga a corregir el generador/HTML y volver a probarlo, nunca a añadir `'unsafe-inline'` por conveniencia. En el build 005.2-NETLIFY-FIX el 404 personalizado no contiene `<style>` ni atributos `style`: `style-src-attr 'none'` sustituye los hashes de atributos del build anterior.
4. Guardar `bun scripts/export-manifest.ts inventory` mediante redirección a un JSON en una ruta controlada **fuera de `out/` y del repositorio**. Verificar con `bun scripts/export-manifest.ts verify <ruta-absoluta-del-manifiesto.json>`; la lista incluye el `_headers` raíz y rechaza variantes anidadas. Revisar manualmente **cada** archivo HTML/TXT/JS/CSS y `_headers`, además de búsqueda de extensiones y patrones de secretos, datos e importes; los patrones y SHA-256 no garantizan confidencialidad. Conservar exactamente los bytes inspeccionados offline; no volver a construir, modificar ni transformar la carpeta después de aprobarla.
5. Completar las puertas humanas de `PREDEPLOY-CHECKLIST.md`, `PRIVACY-AND-RIGHTS.md` y `NETLIFY-READINESS.md`. Sin autorización independiente y explícita de publicación, **detenerse aquí**.

## Subida futura, sólo con autorización explícita

Verificar primero el plan, visibilidad real del proyecto, costos, responsable y tratamiento de logs/cookies. Una URL de despliegue no es intrínsecamente privada: la visibilidad depende de la configuración del proyecto/equipo. En el flujo de [drag-and-drop](https://docs.netlify.com/deploy/create-deploys/#drag-and-drop), el operador autenticado arrastra **el directorio de salida listo para publicar** (con `index.html`, `_headers` y assets), no el repositorio ni un ZIP comprimido, al área de Netlify Drop. Para un sitio drag/drop existente, arrastra la nueva carpeta al área de su pestaña **Deploys**. El servicio publica el deploy exitoso y entrega una URL; no usarlo como ensayo privado antes de autorización. No conectar GitHub ni habilitar auto-publish. El despliegue manual no es un PR Deploy Preview. El [permalink inmutable](https://docs.netlify.com/deploy/deploy-overview/) identifica una versión; la URL principal sirve la versión publicada. Registrar identificador, manifiesto SHA-256, URL, fecha y responsable sin copiar material privado a informes.

Después de la subida autorizada, desde fuera del host: comprobar HTTP/HTTPS, certificado y redirección; `200` para `/`, `/datos/`, `/fuentes/`, `/metodologia/`, `/proyecto/`, `/estado/` y variantes sin barra según normalización real; `404` verdadero y la página de error esperada para una ruta inexistente; MIME, caché, enlaces, JS/CSS/TXT, navegación e hidratación. Inspeccionar **las cabeceras HTTP efectivas** en páginas, error y assets; comprobar consola y reportes CSP Report-Only de los nueve HTML, estilos de 404, red/cookies, móvil, teclado, zoom real 200/400 % y lector de pantalla. No declarar éxito por el archivo `_headers` local ni por un `curl` único. Si una cabecera falta o el comportamiento difiere, NO-GO hasta investigar; no debilitar silenciosamente la CSP.

## Reversión

Conservar y aprobar de antemano un deploy anterior completo, **incluido su `_headers`**, y su manifiesto. En la [pestaña Deploys](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/), seleccionar el deploy exitoso anterior y **Publish Deploy**: el host conmuta a esa versión atómica, sin crear un build nuevo. Confirmar cuál URL principal y permalink sirven los bytes y cabeceras esperados; repetir 404, rutas, CSP, recursos, cachés y red. Si no existe una versión anterior segura (por ejemplo, primer deploy), detener la publicación o restringir acceso según las capacidades aprobadas del proyecto; no prometer un rollback inexistente. La reversión del origen Git no revierte el sitio; aunque aquí no hay integración Git, una futura auto-publicación podría reemplazar la versión revertida. Si hubo exposición, tratarla como incidente: reversión no borra copias, cachés ni logs.
