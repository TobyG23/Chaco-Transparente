# Netlify — puerta para proyecto privado vacío

**Misión 005.5A · 2026-10-17 · alternativa histórica, no elegida en 005.5B-PUBLIC.** El propietario optó por preparar una previsualización **pública**; no seguir este checklist Private salvo decisión posterior expresa. Procedimiento, no ejecución. Este documento permite decidir si solicitar autorización para **crear un proyecto vacío**, no autoriza inicio de sesión, instalación, creación, subida, despliegue, DNS ni acceso de terceros. `publicationAllowed=false` continúa vigente. Usar junto con `NETLIFY-DEPLOYMENT.md`; no confundir esta puerta con la aprobación del artefacto o de una URL de previsualización.

## Panel frente a CLI

El **panel** permite revisar/cambiar la visibilidad predeterminada del equipo y, después de crear un proyecto, inspeccionar la visibilidad individual de producción y previews. La [documentación de creación de deploys](https://docs.netlify.com/deploy/create-deploys/) consultada **no describe un botón del panel que cree un proyecto en blanco sin Git, código generado ni subida**: sus rutas de Git y Drop no cumplen la puerta «crear, comprobar y sólo después subir». La ruta vacía **documentada** es el comando CLI `netlify sites:create --disable-linking`; no se afirma que la interfaz jamás pueda ofrecer otra opción. Si el propietario sólo quiere usar panel, detenerse y solicitar una ruta oficial equivalente antes de actuar.

## Antes de solicitar autorización de creación

- [ ] El propietario identifica la cuenta y el equipo correctos, su rol **Team Owner** y el plan **Credit-based Free**; las cuentas antiguas podrían seguir en un plan *legacy* con controles distintos. La visibilidad Private de Credit-based Free requiere inicio de sesión en Netlify y sólo permite ver el proyecto al Team Owner; no es una contraseña compartida ni una URL secreta. Si se necesita compartir acceso con otra persona, revisar un plan y permisos distintos **antes** de crear.
- [ ] Revisar en **Team settings → General → Visitor access → Default project visibility** el valor real. La opción deseada es **Private for new projects**. Si es Public, cambiarla sólo mediante autorización para modificar ese ajuste y volver a comprobarla **antes de crear**. **Private for all projects** afectaría proyectos existentes: no seleccionarla por accidente. No confiar en la fecha de creación del equipo.
- [ ] Confirmar con el propietario nombre previsto y equipo de destino, presupuesto/condiciones de Free, responsable del proyecto, datos de cuenta, efectos de cambiar visibilidad del equipo y tratamiento de logs/acceso. No registrar credenciales, tokens, cookies ni detalles privados en Git.
- [ ] Obtener autorización independiente y acotada para **crear solamente el proyecto vacío**, e identificar si se autoriza instalar/usar CLI e iniciar sesión en una futura sesión. Esta misión **no otorga** esos permisos.

## Procedimiento futuro, únicamente después de autorización

1. Con el propietario autenticado, comprobar de nuevo equipo, plan Credit-based Free y **Private for new projects** antes de iniciar la creación. Si algo no coincide, **cancelar antes de crear**. No usar Netlify Drop, `netlify create` ni `netlify init`: pueden publicar o configurar integración Git; tampoco vincular GitHub.
2. Ruta de creación vacía documentada: `netlify sites:create --disable-linking` con el CLI autorizado. Elegir el equipo y nombre previstos en los controles del comando y **no** activar CI ni suministrar carpeta de export. `--disable-linking` evita vincular el directorio local; la referencia llama al resultado «empty project», pero **no garantiza expresamente ausencia de cualquier deploy o URL servida**. Inspeccionar el estado inmediatamente después de crear. **Crear el proyecto sigue siendo una acción remota** y requiere aprobación específica.
3. Antes de subir cualquier byte, inspeccionar en **Project configuration → General → Visitor access → Project visibility** los controles **producción y previews por separado**. Ambos deben indicar **Private**. Registrar comprobación de plan, equipo, ID/nombre, ambos estados, ausencia de Git conectado y ausencia de deploy exitoso, sin guardar credenciales. Si el panel sólo presenta opciones tras un primer deploy o no permite corroborar ambas antes de subir, **cancelar la siguiente fase sin subir** y solicitar aclaración a Netlify.
4. Revisar la URL principal asignada en un navegador sin sesión, si existe. Un error, página vacía, login o 404 **no demuestra por sí solo** que la URL o futuras rutas de deploy estén protegidas. El criterio previo es configuración Private verificable en ambos controles y ausencia de contenido subido; la comprobación empírica de URL draft, permalink y assets sólo es posible tras un deploy autorizado. Mantener el proyecto vacío y no compartir enlaces como garantía de privacidad.
5. Detenerse. La autorización para crear **no** cubre CLI deploy, Drop, `--prod`, Git, DNS, artefactos ni promoción. La revisión de bytes y las pruebas sin sesión posteriores figuran en `NETLIFY-DEPLOYMENT.md` y exigen autorización nueva.

## Cancelación / NO-GO inmediato

- El plan no es **Credit-based Free** o no ofrece Private al Team Owner; el equipo, identidad o permisos no están claros.
- No es posible comprobar/fijar **Private for new projects** antes de crear, o la operación afectaría proyectos existentes sin consentimiento.
- La única ruta disponible obliga a subir archivos, conectar Git/CI o desplegar antes de comprobar los controles de visibilidad. No «probar» con el export editorial ni con un archivo señuelo sin autorización de subida.
- Después de crear, producción **o** previews no son Private, los controles no están disponibles, aparece un deploy inesperado, o una solicitud anónima obtiene contenido no autorizado. Detener y evaluar la situación; eliminar o cambiar un recurso remoto exige decisión/permiso propios.
- El operador no puede confirmar condiciones, créditos, límites, jurisdicción o titularidad pertinentes. No asumir que Free elimina el riesgo operativo.

## Créditos y límites; sin garantías implícitas

La documentación oficial indica **USD 0 y 300 créditos por ciclo** para Credit-based Free, sin recarga automática; agotarlos pausa los proyectos web del equipo. Un deploy exitoso de **producción** cuesta **15 créditos**; los **Deploy Previews y branch deploys** no tienen cargo de despliegue, pero el tráfico consume **20 créditos/GB** y **2 por 10.000 solicitudes**. La [tabla oficial del plan](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/) indica un límite de **500 proyectos** en Free, pero no proporciona una tarifa inequívoca para un **draft manual** ni una afirmación específica sobre el costo de crear un proyecto **vacío**: comprobar el saldo y condiciones actuales de la cuenta; no derivar costo cero del nombre «Free» o de la ausencia de build. Un build concurrente en Free no significa que la creación vacía lo utilice. La eventual prueba de la URL del proyecto vacío podría contar como solicitud: comprobar la facturación real.

Estas páginas describen capacidades, no la configuración real de la cuenta del propietario. Reconfirmar interfaz y tarifas en el momento de cualquier autorización.

**Veredicto documental:** solicitar autorización **sólo para la creación vacía**, condicionada a comprobar previamente el ajuste privado del equipo, es defendible; **NO-GO para crear en esta misión y NO-GO para subir, desplegar o afirmar privacidad de URLs alternativas**.
