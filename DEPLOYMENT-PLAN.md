## Arquitectura

Repositorio público → checkout limpio del commit aprobado, **sin** `data/` ni originales en el entorno de build → Bun fijado por lockfile y scripts de instalación deshabilitados → pruebas y export → inspección y manifiesto de archivos SHA-256 → aprobación humana de un artefacto inmutable conservado **offline** → sólo tras autorización independiente de publicación, subida manual al host → CDN/HTTPS/cabeceras definidas para ese mismo artefacto → verificación externa. En Pages Direct Upload, la primera subida puede dejar el sitio accesible en `pages.dev`; una URL de preview tampoco es privada por definición: **no subir** el artefacto para usarlo como staging privado. No conectar automáticamente cada push de `main` a producción; evitar que la carpeta del repositorio, `.next/` o los originales sean raíz pública. El host debe resolver `/datos/` como `/datos/index.html` y servir 404 real. Bajo una subruta se requiere `basePath` y nueva verificación; no basta con cambiar DNS.

2. Ejecutar `bun run lint`, `bun run test`, typecheck **directo** de `@chaco/core`, `@chaco/ingestion` y `@chaco/web`, y `bun run web:verify`. Detenerse ante errores. 5. Con autorización específica de despliegue futuro, publicar **únicamente los bytes del artefacto aprobado por hash**, con configuración de cabeceras validada y un mecanismo de promoción manual. Rollback: restaurar el **artefacto anterior y la configuración de cabeceras asociada**, invalidar/esperar las cachés según proveedor y repetir verificaciones externas. `git revert` no revierte por sí solo bytes ni cabeceras ya servidos. ## Misión 005.1 — inventario local reproducible

Se crearon `scripts/export-manifest.ts` y sus tests **sintéticos** `scripts/export-manifest.test.ts`; no se creó configuración de proveedor. Tras un build fresco, ejecutar desde la raíz `bun scripts/export-manifest.ts inventory` y guardar la salida JSON **fuera de `out/` y del repositorio** mediante redirección a un archivo controlado por el operador. Para cotejar más tarde los mismos bytes: `bun scripts/export-manifest.ts verify <ruta-absoluta-del-manifiesto.json>`. El script usa exclusivamente `packages/web/out/`, enumera rutas relativas ordenadas, tamaños y SHA-256; exige las nueve rutas HTML, admite sólo la forma observada de TXT y assets JS/CSS, rechaza symlinks/junctions/archivos especiales, hard links con `nlink > 1` y rutas o extensiones imprevistas. Un directorio vacío de build ID de Next puede aparecer y está permitido bajo `_next/`; no representa un archivo aprobado. Estas comprobaciones de rutas no dan garantías frente a modificaciones concurrentes adversariales ni sustituyen congelar el artefacto tras validarlo. Falla si cambia un byte, falta o se añade archivo. No escribir manifiestos con contenido privado en un lugar compartido. La salida es metadato, no copia de los archivos.

Este inventario **no** inspecciona semánticamente todo contenido ni garantiza ausencia de secretos, datos o importes embebidos en HTML/JS/TXT: requiere inspección humana y pruebas de export. Si un futuro `_headers` pasa a integrar el artefacto, el script debe adaptarse con revisión y pruebas específicas antes de generar un manifiesto aprobable; hoy lo rechaza intencionalmente. El hash sólo identifica bytes: después de aprobar el manifiesto, evitar reconstruir o transformar el artefacto entre revisión y promoción. Pruebas en host, accesibilidad y decisiones del propietario son puertas independientes.

Antes de Misión 005.1 no se habían creado scripts ni archivos de configuración de proveedor. Ahora existen únicamente scripts locales; las puertas (`web:verify`, test del export, `.gitignore`) permanecen y no autorizan publicación.
